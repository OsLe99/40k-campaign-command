## Application architecture
Organize `src/` into pages, feature components, layout/navigation, reusable UI, hooks, contexts, services, shared types, and `lib/` configuration. Use typed Supabase services for persistence, an authentication context for session state, and shared query/mutation hooks for loading, caching, invalidation, and errors. Keep authorization authoritative in PostgreSQL rather than route guards.
Provide public campaign browsing/detail, player and army profiles, battle history/reports/photos, and standings. Authenticated pages cover account/profile management, armies, campaign enrollment, battle submission, and confirmation/dispute queues. Campaign administration covers participants, campaign details, corrections, disputes, and moderation; global administration adds cross-campaign moderation and role management.
Include accessible forms and navigation, mobile layouts, pagination, and loading, empty, error, permission-denied, and not-found states. Missing Supabase configuration must show actionable setup guidance rather than a misleading working demo.
## Database and authorization
Create ordered, version-controlled migrations under `supabase/migrations/`, reproducible local fixtures, database authorization tests, and generated TypeScript database types.
Retain the specified profiles, campaigns, campaign members, armies, army images, battles, battle participants, and battle images. Add the relationships and state required by the stated behavior:
* Separate campaign publication visibility from Upcoming/Active/Completed lifecycle status, and include background lore and update timestamps.
* Add campaign-army registration so an army can participate in multiple campaigns while retaining one owner.
* Store global administrator assignments separately from editable profiles and campaign membership. CampaignAdmin privileges remain scoped to one campaign. Bootstrap the first global administrator through a controlled administrative procedure, never public signup metadata.
* Add per-participant battle responses, dispute reasons, revision tracking, and a minimal moderation audit trail. Keep any required `is_confirmed` compatibility value server-maintained rather than independently client-editable.
Enforce unique usernames/memberships/registrations/participants, valid dates and scores, ownership, campaign consistency, indexes on common filters, and intentional deletion behavior. Preserve historical battle integrity rather than silently cascading away recorded results when a player leaves a campaign.
Enable RLS and explicit least-privilege grants on all exposed tables. Public reads expose published content only, without authentication emails or administrative role records. Owners manage permitted profile/army fields; campaign administrators manage only their campaigns; global administrators have explicitly authorized moderation powers. Prevent self-promotion and protect role, ownership, battle status, and confirmation fields from ordinary direct updates. Ensure views and functions do not bypass intended visibility.
## Transactional battle lifecycle and standings
Implement secured PostgreSQL functions for battle submission, participant responses, corrections, and administrative resolution. Each function validates the authenticated caller and all related records within a transaction; privileged functions use a fixed search path and restricted execution grants.
Submission requires at least two distinct campaign members using their own campaign-registered armies. Lock relevant state when processing responses to prevent concurrent confirmations or edits from producing inconsistent results. A submitter attests only to their own result; every other participant must confirm before the battle counts. Any dispute blocks automatic confirmation; campaign/global administrators may resolve or reject it with an audit record. Material edits invalidate prior confirmations.
For the initial multiplayer result model, allow exactly one winner with all other participants losing, or all participants drawing. Team-based outcomes are outside the initial scope unless separately specified.
Compute standings and statistics from confirmed battles scoped to the selected campaign. Proposed default: 3 points for a win, 1 for a draw, 0 for a loss; sort by points then wins, preserve equal ranks on ties, and use a stable display order. Nullable victory points remain optional report data rather than an implicit tie-breaker. Keep the scoring calculation centralized and tested.
## Authentication and photographs
Implement email/password registration, verification, login/logout, persisted sessions, profile creation through a protected signup trigger, and handling of unverified accounts, expired sessions, and callback failures. Role checks must not trust client-editable user metadata.
Make authentication callbacks compatible with HashRouter and the GitHub Pages repository base path. Prefer PKCE query-code handling at the application entry URL before route rendering; document its same-browser/device requirement and provide useful recovery for failed verification exchanges. Configure allowed redirects for development and the deployed site.
Use Supabase Storage with private buckets and authorized reads/signed URLs so unpublished content is not exposed through permanent public URLs. Store object paths with image metadata and enforce ownership/campaign permissions, size limits, and supported image MIME types. Support army main images, galleries, battle photographs, captions, and permitted deletion. Handle failed uploads, metadata writes, expired signed URLs, and retryable object cleanup; Storage and database writes are not one atomic transaction.
